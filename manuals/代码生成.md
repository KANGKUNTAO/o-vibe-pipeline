# 代码生成手册 — 分层契约与测试纪律(Cocos 2D 版)

> 五步工作流第 3 步(白盒)起,**所有游戏代码按本手册写**。白盒代码不是临时代码——分层和契约从第一行就成立,后面换资产、换 UI 都不动逻辑。
> 蓝本:GameFactory-3A `agent_skills/code_gen/` 层,重写为 Cocos Creator 2D + TypeScript 版。
> 状态:协议版(2026-09-29),随 001 实战修订。

## 写代码前按序读(权威顺序,越前越优先)

1. 游戏工程的《立项卡》《设计说明书》《机制契约》(已存在则必读)
2. 本手册
3. `adapters/cocos/引擎上下文.md`(API 纪律与版本基线)
4. `adapters/cocos/引擎操作.md`(编辑器与构建工具用法)
5. 参考示例(组件库副本、`tools/cocos-creator-local-mcp/skills/`):**只读参考,不是模板、不是继承基类、不是运行时依赖**;看最小够用的部分,禁止整目录扫描

引擎与平台以《立项卡》为唯一事实:不许换引擎、不许混用 API、文档缺失时如实报告而不是自行发明。

## 依赖方向(第一红线)

```
UI → 机制 → 引擎
```

- **机制层**(游戏工程 `assets/scripts/game/`):游戏规则、状态、结算、经济。**纯 TypeScript,零节点依赖**:不 import Sprite/Button/Prefab 等展示类,不查找节点,不播放动画,不碰 Canvas。
- **UI/组件层**(`assets/scripts/components/`、`assets/scripts/ui/`):布局、绑定、反馈。只通过机制层公共接口读写;**禁止私存游戏规则状态**(禁止"第二份状态"——UI 缓存一份血量、机制层又存一份,必然失同步)。
- **引擎层**:Cocos API。按引擎上下文手册的边界使用,不绕过、不碰私有内部。
- 反向依赖 = 结构性错误:**UI 里出现规则判断、机制里出现节点操作,都是混层**。发现即停(见停止条件)。

## 机制契约(层与层的咬合点)

每个游戏维护一份 `docs/机制契约.md`,三张表 + 一张绑定清单:

| 表 | 内容 | 示例 |
|---|---|---|
| 状态(State) | UI 可读的值:字段名 + 类型 + 含义 | `moves: number — 剩余步数` |
| 事件(Event) | 机制层对外广播的通知 | `gem:cleared — {ids, combo}` |
| 命令(Command) | UI/运行时可调用的动作 | `restart()`、`useBoost(id)` |

**UI 绑定清单**:每个可交互 UI 元素 → 绑定的命令;每个展示元素 → 绑定的状态或事件。**禁止无绑定的装饰按钮。**

契约规则:

- 契约列出的表面是 UI **唯一**可依赖的东西。机制内部怎么重构都行,改契约表面 = 设计变更(触发任务台账重开,见玩法切片手册)。
- 契约从白盒第一天就存在,随里程碑演进;八件套组件的对外事件(M4 组件库接口约定)直接登记进契约。
- 平台能力(广告/分享/登录)的调用入口也进契约:机制层发命令/收事件,平台适配层(`assets/scripts/platform/`)负责真正调 SDK,UI 不直接碰平台 SDK。

## 表现措辞 → 机制信号翻译

设计书用的是表现语言,落到机制层必须是信号。写代码前先做这张翻译:

| 设计书说 | 机制层必须有 |
|---|---|
| 血条 / 步数条 | 当前值 / 最大值状态 |
| 胜利画面 / 结算界面 | 胜负状态 + 结算事件 |
| 重开按钮 | 重开命令 |
| 连击特效 | 连击计数状态 + 连击事件 |
| 奖励弹窗 | 奖励发放事件(发放走经济系统,展示归 UI) |
| 红点 | 系统状态派生(红点组件只订阅事件,不自己算业务) |
| 星级评价 | 得分状态 + 星级判定规则(机制层算,UI 只显示) |

## 测试纪律(不许自欺)

- **机制层必须可脱离 UI 验证**:纯逻辑模块在 Node 环境可单测(如 `npx tsx` / vitest,不启动编辑器)。做不到"脱离 UI 可测"本身就是一个混层信号。
- 每条验收标准(来自立项卡/设计说明书)映射四件套:**源码 + 可观察行为 + 契约项 + 一个"行为缺失会失败"的检查**(自动化测试,或可重复的手动步骤 + 录屏证据)。
- 测试必须可能失败:不许空断言、无条件通过、只构造不验证。
- **修复失败不许改弱、删除、跳过测试来"过关"**;只改产品代码,修最小根因。
- 修 bug 改所属层:资产问题不塞进玩法代码补丁,UI 问题不改机制,引擎用法问题不改业务代码绕过。

## 修复与证据

- 每次修复记录四要素:症状 → 所属层 → 修复 → 复验证据(新录屏或新测试输出)。
- 游戏工程 `evidence/` 只追加不改写;旧证据不因新修复失效,但**不能顶替**复验所需的新证据。

## 停止条件(发现即停,如实报告后再动)

- 混层:UI 写规则、机制操作节点、两层私建同一状态
- 契约表面之外的隐式依赖、无绑定装饰按钮
- 改弱测试来通过、无证据声称"可玩/已修好"
- 引擎 API 用法超出引擎上下文手册基线且未实测验证
- 参考示例被当作模板抄进工程、或成了运行时依赖
