# 玩法切片手册(M1)— 需求 → 白盒 → 可玩循环

> 五步工作流第 2 步(规划设计)和第 3 步(白盒)的展开。接手新游戏后,按本手册把一条需求变成"能玩的丑版本"。
> **本手册是操作协议,不是介绍文**:每个产出有格式,每个确认有记录,每条纪律可执行。
> 蓝本:GameFactory-3A `game_design/` 五册平移 + 2D 休闲品类适配。状态:协议版(2026-09-29),随 001 实战修订。

## 产出物清单(按顺序做,全部放游戏工程)

1. `docs/立项卡.md` — 第 1 步(明确需求)的答卷
2. `docs/设计说明书.md` — 章节分解 + 交互规格 + 语义色板图例
3. `docs/资产清单.md`(manifest)— 资产 ID 契约,**从此冻结**
4. `docs/任务台账.md` — 任务状态机,**贯穿 M1–M5 全程**
5. 白盒工程(可玩)+ `evidence/白盒.mp4`

## 立项卡模板(复制填空,8 项无空缺才算过)

```markdown
# 立项卡
- 游戏代号:
- 目标平台:(决定交付手册与验收附录;当前已装平台适配:微信小游戏)
- 引擎:(当前已装引擎适配:Cocos Creator 3.8.8)
- 品类:
- 核心循环(一句话):
- 变现模式(选项随平台,如微信:纯广告 / 内购 / 混合;未定则本卡未完成)
- 内容量目标(关数/天数 + 基线依据):
- 八件套范围:做 [ ] / 裁剪 [ ](逐项列)
- 美术风格 + 参考图路径:
- 预算:默认零成本(免费额度内);超支需批准
- 附:目标平台当期规则核实结论与日期;性能口径(机型/帧率/内存)
```

## ID 追溯体系(设计即冻结,贯穿到证据)

立项卡逐条编号为**需求 ID**,再加三类:

| ID 类型 | 格式 | 例 | 作用 |
|---|---|---|---|
| 需求 | `req-NNN` | `req-003 核心消除循环` | 立项卡每行一个,任务必须能追到它 |
| 节拍 | `beat-NNN` | `beat-004 首次消除反馈` | 一局/一关内的有序节拍(开局→操作→反馈→结算→重开) |
| 界面 | `screen-NNN` | `screen-002 结算界面` | 每个界面一个,含进入/退出条件 |
| 资产 | `gXXX-类别-名称-序号` | `g001-spr-gem-red-000` | 详见下文资产 ID 规范 |

规则:

- **任务必须引用它实现的需求/节拍/界面/资产 ID**;没有 ID 引用的工作不存在于计划中。
- 需求条目**不许静默丢弃**:要么实现,要么标记 `not_applicable` 并给理由。
- 叙事品类的"章节"在本管线适配为**关卡分档或系统模块**;节拍照常。

## 设计说明书(内容要求)

- **章节分解表**(品类适配版),每章/档一行:`id、名称、引用需求ID、预计时长、进入条件、目标与节拍(有序)、引入机制、退出条件、重试与存档、资产与界面引用、验收`。
- 分解**按玩家的时间顺序,不按资产类型**。先粗排全部章节,再只细化当前可玩切片;后续章节保持轮廓级,但资产与界面需求不许从粗排里漏掉。
- **有状态变体显式列出**(满/空、开/关、昼/夜、普通/强化)——变体不一定新资产,先说清靠贴图、动画还是运行时状态实现。
- **连续性检查**:跨章节边界,位置、持有物(货币/道具)、已解锁内容、未完成目标保持一致。
- **交互规格**(下文六段式)逐特性展开;**语义色板图例**(下文)先于白盒存在。

## 交互规格(六段式,逐特性)

每个**可交互特性**(核心动词、引导、结算、每个八件套入口、分享、看广告)写一段:

1. **意图**:玩家想要什么,这个动作怎么被发现(入口在哪、何时可见)
2. **规则**:前置条件、合法操作、消耗、结果
3. **输入**:触发、瞄准/选择、确认、取消、打断
4. **状态**:不可用 / 就绪 / 激活 / 成功 / 失败 / 恢复(按适用)
5. **反馈**:画面内表现 + HUD + 音效 + 动效,每个状态转换对应什么
6. **验收**:玩家能理解、能完成、能重复的判据

硬规矩:每个可点 UI 元素必须映射到机制契约里的一条**命令**;每个展示元素映射到一条**状态或事件**;**禁止无绑定的装饰按钮**。八件套入口的命令/事件用 M4 组件库接口约定,登记进 `docs/机制契约.md`。

## 白盒语义色板(图例先于白盒存在)

白盒开工**前**,先在设计说明书里定死图例:

| 字段 | 例 |
|---|---|
| semantic_id | `sem-player` / `sem-obstacle` / `sem-collectible` |
| 含义 | 玩家可控 / 危险 / 可收集 |
| 颜色 | 具体色值 |
| 辅助线索 | 形状 / 文字标签 / 图标(必须与颜色并存) |
| 适用对象 | 哪些资产 ID |

规矩:

- 只有**功能或属性影响玩家决策**的类别才配不同颜色;别给每个数值差异一个色相。
- 颜色必须配非颜色线索(形状/标签/图标);对比度要在实际画面上可辨。
- **禁止用颜色泄露玩家不该知道的信息**(隐藏/伪装/未揭示属性不得改变玩家可见颜色)。
- 环境用中性弱色,别抢主体;成品资产替换后保留线索语义。
- 图例同时用于场景占位、缩略图和资产清单备注。

## 任务台账协议(贯穿 M1–M5)

`docs/任务台账.md`,一张表,一次维护:

| 字段 | 说明 |
|---|---|
| `id`、`title` | 稳定身份 + 具体结果 |
| `所属` | 阶段或系统(哪个章节/模块/八件套件) |
| `引用` | req / beat / screen / asset IDs(可追溯性) |
| `工种` | design / asset / mechanic / ui / assembly / validation |
| `依赖` | 前置任务 ID |
| `验收` | 可观察的完成条件 |
| `状态`、`阻塞原因` | 当前态与卡点 |
| `证据` | 测试/构建/录屏/截图引用 |

状态机:`needs_detail → ready → in_progress → review → done`,另有 `blocked`。

- `ready` 才许开工:输入齐、验收明确、依赖完成。
- 进 `review` 要挂产出与证据;`done` 仅当验收通过。
- **设计或契约变更 → 受影响任务一律重开**,旧证据不算数,下游结果重查,不许拿旧版证据顶替。
- 生成、装配、验证**分开记账**;**"生成了/写完了"永远不等于"可玩"**。
- 父里程碑(白盒可玩/垂直切片/内容完成/提审)只在子任务全部完成且端到端验收通过后勾。

## 逐项确认纪律(禁止笼统)

设计定稿前,产出一张逐项明细表(`item_id / 所属 / 检查项 / status / 参考 / 问题`):

- `status` 三值:`confirmed` / `missing` / `not_applicable`(**必须给理由**)。
- **明文禁止"以上都已覆盖"式总结**——逐行有 status、有理由。
- `missing` 清零才能宣布设计就绪、进入白盒。
- 设计确认 ≠ 实现完成 ≠ 试玩完成,三者分开记账。

## 资产 ID 规范(冻结即契约)

- 格式:`<游戏代号>-<类别>-<名称>-<序号>`,全小写,连字符分隔。类别枚举:`spr`(精灵)、`ui`、`eff`(特效帧)、`tileset`(图块集)、`audio`、`font`、`scene`、`prefab`。例:`g001-spr-gem-red-000`。
- manifest 文件 `docs/资产清单.md`,表头:`ID | 类别 | 用途 | 规格 | 状态 | 出处 | 许可证`。规格 cell 支持机器可读 token:`128x128`(尺寸)、`frames=N`(帧数)、`alpha`/`nonalpha`(透明底)——`tools/scorer/` 与 `tools/placeholder/` 直接消费这些 token。
- **ID 只增不改**:换素材换文件,不换 ID;代码只引用 ID。
- 白盒第 1 天就建 manifest,占位资产也登记(状态=占位),文件可由 `tools/placeholder/gen.py` 批量生成。

## 白盒三原则

1. **占位也挂正式 ID**:色块 PNG 也要有 ID、进 manifest,后面精修是"替换"而不是"重接"。
2. **核心循环全通**:启动 → 玩一局 → 胜或负 → 结算 → 重开,一次不缺;引导灰框走通。
3. **录屏留证**:`evidence/白盒.mp4`,一段完整循环。

## 白盒操作路径(引擎操作见 `adapters/cocos/引擎操作.md`)

**写代码前先读 `manuals/代码生成.md`(分层契约)与 `adapters/cocos/引擎上下文.md`(API 纪律)**——白盒代码也按契约分层,不是临时代码。然后:

1. `cocos_local_open_project`(waitForBridge)打开游戏工程
2. 组件脚本:`cocos_local_create_component_script`;复杂玩法可先 `cocos_local_create_architecture_skeleton` 再裁剪
3. 搭场景:`cocos_local_apply_scene_blueprint`(节点/组件/属性一次成型)
4. 占位素材:按语义色板生成纯色/文字 PNG 写进 `assets/`,再 `cocos_local_place_sprite_assets` 挂进场景
5. 编辑器内运行验证,录屏

## 白盒过关 checklist(全勾才进资产精修;逐项给证据)

- [ ] 核心循环录屏完整(启动→一局→结算→重开)
- [ ] 无阻断 bug(卡死/崩溃/无法返回)
- [ ] 语义色板图例先行并在场景中执行(颜色+非颜色线索)
- [ ] 代码分层与机制契约就位(UI→机制→引擎,绑定清单齐)
- [ ] manifest 已建,玩法出现的每个可见元素都有 ID
- [ ] 主要动词手感真实(不是"看动画",是玩家在操作)
- [ ] 设计说明书八问全部有答案
- [ ] 任务台账在用(状态机、证据挂接),逐项确认表 `missing` 清零
- [ ] 发现的玩法问题清单已列出(白盒阶段改,不上成品资产后再改)
