# vibe-pipeline 总入口 — AI 工作流路由

> **你是 AI(编程智能体)。接到"用 vibe-pipeline 做游戏"的任务时,本文件是你第一个读的文件。**
> 它告诉你:按什么顺序做事、每一步读什么、做到什么程度才算"完成"。
> 本管线只服务一个目标:**把一条 2D 微信小游戏需求,做成可提审的成品**——不是可玩切片,是成品。

## 一句话理解这条管线

**需求 → 规划 → 白盒 → 资产精修 → 实机验收**,五步走完,每步有过关标准,不过关不进下一步。

## 仓库定位与路径约定(两仓分离,硬性规定)

- **本仓库 = 管线正本**:手册(`manuals/`)、可执行工具(`tools/`)、商业化组件库正本(`adapters/cocos/`)。**本仓库不放任何具体游戏的内容**。
- **每个游戏一个独立工程仓**(如 001 号试验游戏 `E:\AiProject\Vibe-OFrame`):只放该游戏自己的场景、代码、资产副本。
- 游戏工程根目录放一个 `AGENTS.md`,内容一句话:接到任务先读本仓库的 `manuals/总入口.md`,再回到本工程干活。
- 本文件及所有手册中的路径,`<PIPELINE>` 指本仓库根目录(当前为 `E:\AiProject\vibe-pipeline`);游戏工程内部路径相对该工程根。
- 组件库正本在 `<PIPELINE>/adapters/cocos/`,游戏工程里放**副本**(拷贝过去),不跨仓引用。
- 引擎只有一个:**Cocos Creator 3.8.8,2D 项目**,目标平台**微信小游戏**。不混用其他引擎,不因"更容易做"换引擎。

## 端到端五步工作流

每个游戏任务都按这个顺序。**没有规划不许直接写代码,没有白盒不许直接做资产。**

### 第 1 步:明确需求

搞清楚八件事,缺了就问用户;只缺一件时,可先给默认值再请用户确认:

1. **品类**(消除 / 合成 / 放置 / 跑酷等休闲品类;本项目不做重度游戏)
2. **核心玩法循环**用一句话说清(例:"交换相邻元素,三个相同即消除得分,步数用尽结算")
3. **变现模式**——纯广告(免版号)还是内购(需版号)。**这条影响后面所有合规工作,必须第 1 步就定**
4. **内容量目标**(例:消除类 ≥40 关;其他品类基线立项时定)
5. **系统范围**:商业化八件套(签到、商店/兑换、分享、排行榜、红点、广告位、设置、成就/任务)哪些做、哪些裁剪,白纸黑字定下来
6. **美术风格** + 参考图(至少 1 张)
7. **预算**(默认零成本方案:云端 API 免费额度内;要花钱必须先请示)
8. **验收标准**(默认 = `<PIPELINE>/manuals/验收清单.md` 全部 8 条)

**产出**:一份《立项卡》(写在游戏工程 `docs/立项卡.md`),上面 8 项逐条填好。
**过关标准**:8 项无空缺,变现模式已定。

### 第 2 步:规划设计

把需求翻译成可开工的图纸:

- **玩法切片说明书**:核心循环、一局的完整流程、胜负判定、失败/重开逻辑、引导流程。
- **系统清单**:第 1 步定下的八件套范围,每个系统一句话说明入口和作用。
- **资产清单 + 冻结资产 ID**:每个资产一个稳定 ID(格式:`<游戏代号>-<类别>-<名称>-<序号>`,例 `g001-spr-hero-000`)。**ID 从此刻起不再变**,白盒占位和最终成品用同一个 ID,后面替换资产不改动代码引用。
- **内容量规划**:关卡分档(例:40 关 = 4 档难度 × 10 关),每档引入什么新机制。
- **里程碑**:白盒可玩 / 垂直切片(1 关成品质量)/ 内容完成 / 提审,四个时间点。

**产出**:游戏工程 `docs/设计说明书.md` + `docs/资产清单.md`(含 ID 表)。
**过关标准**:核心循环能被一个不懂游戏的人看说明书复述出来;资产清单覆盖玩法切片说明书里出现的每一个可见元素。

### 第 3 步:白盒

用最丑但最快的方式让游戏"活"起来:

- 纯色块、程序化图形(色块+文字)当占位资产,**占位资产也要挂上正式资产 ID**,标记 `状态=占位`。
- 在 Cocos Creator 里(经 cocos MCP 操作编辑器,见 `adapters/cocos/`)把核心循环完整跑通:进入游戏 → 玩一局 → 赢或输 → 结算 → 重开。引导流程也用灰框 UI 走一遍。
- **不许等美术**。白盒阶段发现的玩法问题,成本是色块级;上成品资产后再改,成本翻十倍。
- 构建、运行、**录屏**:一段从启动到重开的完整视频。

**产出**:可玩白盒工程 + 白盒录屏(存游戏工程 `evidence/白盒.mp4`)。
**过关标准**:录屏里核心循环完整走通,无阻断性 bug。**"能编译、能启动、日志无报错"都不算过关。**

### 第 4 步:资产精修

按资产清单逐件把占位换成成品。每件资产走这个流程:

1. **生成**:用可用的生成工具(云端 API 免费额度内;付费先请示,报价格等批准)。
2. **质检**:跑 `<PIPELINE>/tools/` 下的评分器(调色板一致性、帧间一致性、尺寸规格——工具落地前先人工对照参考图检查)。不达标 → 回到 1 换提示词重试;仍不达标 → 进 3。
3. **换有授权的来源**:用明确可商用的素材源,**记录出处与许可证**,写进资产清单。
4. **都不行 → 如实上报**:说清缺什么、试过什么、建议怎么降级。**不许拿劣质资产默默充数。**
5. 替换后**回归**:该资产涉及的玩法流程重跑一遍,确认没被换坏(尺寸、锚点、遮挡、动画帧数)。

**产出**:更新后的资产清单(每件:ID、状态、出处、许可证、质检结果)。
**过关标准**:清单里没有 `状态=占位` 的资产(或占位项已单独列出并经用户同意保留);每件有出处记录。

### 第 5 步:实机验收

成品质量的最终关卡:

1. 构建微信小游戏包。
2. 微信开发者工具 + **真机**完整玩一遍:核心循环、八件套每个界面、引导、断网重连。
3. **录屏**留证。
4. 对照 `<PIPELINE>/manuals/验收清单.md` 逐条打勾,不过的修完重验。
5. 白盒和资产阶段的旧证据**不算数**,这一步重新录。

**产出**:验收清单打勾版 + 每条的证据文件路径(游戏工程 `evidence/` 目录)。
**过关标准**:8 条全勾。差任何一条,游戏就不叫成品,叫半成品,如实告诉用户差在哪。

## 贯穿全程的工作纪律(从 GameFactory-3A 平移,任何一步都适用)

1. **白盒先行**:先证明"好玩/能玩",再谈"好看"。
2. **资产 ID 稳定**:ID 在第 2 步冻结,占位与成品同 ID,换资产不动代码。
3. **验收即录屏**:任何"我做完了"都要有当时的运行证据。"能编译"不算完成,"我看着没问题"不算完成。
4. **规范尽量写成代码**:能用脚本/评分器检查的事(包体大小、调色板、帧一致性),不靠人眼。可执行的规范才有约束力。
5. **出处留痕**:每个成品资产记录来源与许可证;生成工具、提示词、日期一并记录。
6. **凭据安全**:API key 只放环境变量或本地密钥文件,**绝不提交进仓库**。

## 完成规则(红线)

- 不许因"更容易做"偷换游戏类型、引擎或目标平台。
- 玩法、资产、UI 是三个独立交付物,各自验收通过才算数,不许互相打包声称完成。
- **绝不因为"代码写完了"就说游戏可玩**。构建、实玩、录屏、逐条评审,是四种独立证据,缺一不可。
- 发现自己做不到(工具缺、额度不够、质量不达标),**如实上报缺口**,不许静默降级。
- 凭据不入库;不确定要不要提交的文件,先问。
